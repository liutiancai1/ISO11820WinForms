## 13.2 架构演进之路

### 13.2.1 V1.0的教训：大泥球架构

回顾第4章的开篇——我们描述了V1.0版本的痛点：

| 问题 | 后果 | 第12章的分析 |
|------|------|-------------|
| 所有逻辑堆在`MainForm.cs` | 文件5000+行，改一处崩一片 | 上帝类(God Class) |
| `SerialPort`直接作为UI私有字段 | 换硬件必须改UI代码 | 违反依赖倒置原则 |
| 测试需要真的烧到1000℃ | 风险极大，无法自动化 | 无法单元测试 |

### 13.2.2 V3.0的重生：分层架构

吸取教训后，V3.0引入了第4章设计的分层架构，核心改变是**依赖方向**：

```
Forms(UI) → Services(BLL) → Core(核心算法) → Models(数据)
                ↓
         Utilities(基础设施)
```

> 💡 **想一想**
>
> 回顾第4章的依赖倒置原则——`Core/TestMaster1.cs`中的温控算法是否直接依赖了`SerialPort`？如果没有，它是通过什么机制获取传感器数据的？（提示：查看`DaqWorker`的事件机制）

### 13.2.3 全局上下文：SystemContext单例

在WinForms中，多个窗体（主窗体、参数设置、校准）需要共享硬件连接和状态。项目通过`Global/SystemContext.cs`的单例模式解决：

```csharp
// Global/SystemContext.cs
public class SystemContext
{
    public static SystemContext Current { get; } = new SystemContext();
    
    public DaqWorker Daq { get; private set; }        // 数据采集
    public TestMaster1 Master1 { get; private set; }   // 试验控制
    public ProductMasters Masters { get; private set; } // 产品管理
    
    private SystemContext()
    {
        var sensorDict = new SensorDictionary();
        Daq = new DaqWorker(sensorDict);
        // ... 初始化其他服务
    }
}
```

任何窗体只需`SystemContext.Current.Master1`即可获取控制器实例，避免了构造函数层层传递。

## 13.3 核心技术攻关

### 13.3.1 多线程数据采集（解决UI卡顿）

回顾第8章的异步编程——`Services/DaqWorker.cs`使用`System.Threading.Timer`在后台线程采集数据：

```csharp
// Services/DaqWorker.cs
private void DoWork(object? state)
{
    // 后台线程执行耗时I/O，UI线程完全自由
    if (_isSimulationMode)
        DoSimulationWork();    // 仿真模式
    else
        DoHardwareWork();      // 真实串口，可能耗时200ms+
}
```

由于后台线程不能直接更新UI控件，`Forms/MainForm.cs`中使用`Invoke`线程封送：

```csharp
// Forms/MainForm.cs
private void OnSensorDataReceived(object sender, SensorDataEventArgs e)
{
    if (this.InvokeRequired)
    {
        this.Invoke(new Action(() => OnSensorDataReceived(sender, e)));
        return;
    }
    lblTemp1.Text = e.Temp1.ToString("F1");  // 安全更新UI
}
```

> ⚠️ **注意：这正是第7章代码审查清单中的第一条**
>
> "串口回调在后台线程，严禁直接访问UI控件，必须用`Invoke`"——这不是理论，在本项目中就是这么做的。

### 13.3.2 有限状态机（解决复杂流程管理）

回顾第5章的状态机设计——`Core/TestMaster1.cs`通过`switch`状态机管理整个试验流程：

| 状态 | 职责 | 转换条件 |
|:---|:---|:---|
| **Idle** | 等待用户指令 | 用户点击"开始加热" → `Preparing` |
| **Preparing** | PID升温至750℃ | 温度达标且稳定 → `Ready` |
| **Ready** | 维持恒温，计算漂移 | 用户点击"开始记录" → `Recording`；温度失稳 → `Preparing` |
| **Recording** | 记录数据，检测火焰 | 达到设定时间或满足判定条件 → `Complete` |
| **Complete** | 停止记录，生成报告 | 自动复位 → `Preparing` |

```csharp
// Core/TestMaster1.cs
protected override void DoWork(object? state)
{
    switch (Status)
    {
        case MasterStatus.Preparing: DoPreparing(); break;
        case MasterStatus.Ready:     DoReady();     break;
        case MasterStatus.Recording: DoRecording(); break;
        // ...
    }
}
```

> 🔍 **案例实战：状态机的价值**
>
> 如果不用状态机，`DoPreparing()`中的升温逻辑、稳定性检查、漂移计算将全部堆在一个巨大的`if-else`嵌套中。第5章说"状态机让每个状态的逻辑独立、可测试"——在本项目的`TestMaster1.cs`（23KB）中，这一优势体现得淋漓尽致。

### 13.3.3 仿真系统（解决硬件解耦）

回顾第7章的Mock First策略和第9章的SIL仿真——`Services/SensorSimulator.cs`不是返回随机数的玩具，而是遵循热力学规律的数学模型：

```csharp
// Services/SensorSimulator.cs
if (_currentFurnaceTemp1 < targetTemp)
{
    double heatingRate = _config.HeatingRatePerSecond * 0.8;
    _currentFurnaceTemp1 += heatingRate + GetFluctuation();
}

private double GetFluctuation()
{
    return (_random.NextDouble() - 0.5) * 2 * _config.TempFluctuation;
}
```

**无缝切换**：通过`appsettings.json`的一行配置，在仿真模式与生产模式之间切换——上层代码（`MainForm`和`TestMaster1`）完全不知道数据来源。

```csharp
// Services/DaqWorker.cs 构造函数
_simulationConfig = ConfigurationHelper.GetSection<SimulationConfiguration>("Simulation");
_isSimulationMode = _simulationConfig?.EnableSimulation == true;
```
