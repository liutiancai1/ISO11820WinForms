## 9.1 工业软件验证体系

工业软件不同于互联网App，其核心诉求是**确定性**和**安全性**。一个未经充分测试的逻辑错误可能导致设备损坏甚至威胁人员安全。

### 9.1.1 V模型：开发与测试的对应关系

V模型强调每个开发阶段都有对应的验证阶段——回顾前几章的产出物，每一份都对应着一套测试：

| 开发阶段（左侧） | 对应章节 | 验证阶段（右侧） | 验证内容 |
|---|---|---|---|
| 用户需求 | 第3章 SRS | **性能确认(PQ)** | 连续72小时运行，内存不泄漏 |
| 功能规格 | 第3章 F1-F4 | **运行确认(OQ)** | 每个功能模块是否按预期工作 |
| 详细设计 | 第5章 类图/状态机 | **安装确认(IQ)** | 软硬件环境是否具备 |
| 编码实现 | 第8章代码 | **单元测试(UT)** | 单个类或函数是否正确 |

> 📘 **知识拓展：OQ测试不只是"能通"**
>
> 对第5章设计的串口通信类进行OQ验证时，不仅测试"正常通信"，还要测试：断电恢复后能否自动重连？收到乱码时软件是否崩溃？主线程卡死时后台线程是否受影响？这些都对应着第3章定义的非功能性需求。

## 9.2 测试用例设计方法

测试用例的设计不能凭直觉，需要科学的方法论来保证**覆盖率**。

### 9.2.1 边界值分析

大量软件错误发生在输入范围的**边界**上，而不是中间。

例如第8章实现的参数设置界面，目标温度范围100-1100：

| 测试点 | 数值 | 类别 | 预期结果 |
|--------|------|------|----------|
| Min-1 | 99 | 无效 | 边框变红，提示"超出范围" |
| Min | 100 | 有效 | 正常接受 |
| Normal | 750 | 有效 | 正常接受 |
| Max | 1100 | 有效 | 正常接受 |
| Max+1 | 1101 | 无效 | 边框变红，提示"超出范围" |

### 9.2.2 决策表测试

针对逻辑复杂的报警系统，决策表能理清各种条件组合。以不燃性试验的报警逻辑为例：

| 规则 | 温度>800℃ | 传感器断线 | 安全锁开启 | **紧急停止** | **声光报警** |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | Y | — | Y | **X** | **X** |
| 2 | Y | — | N | **X** | **X** |
| 3 | N | Y | — | **X** | **X** |
| 4 | N | N | — | | |

> 💡 **想一想**
>
> 对照第5章的状态机设计——规则1和2进入"Alarm"状态后，哪些按钮应该被禁用？这个测试用例是否覆盖了第5章5.3.3节的交互逻辑表？

### 9.2.3 故障注入

工业现场环境恶劣，必须测试系统在非正常状态下的鲁棒性：

| 故障类型 | 注入方式 | 对应第3章的NFR |
|----------|----------|---------------|
| **硬件断连** | 运行时拔掉USB转串口线 | 断线保护：1秒内切断加热器 |
| **数据异常** | 发送CRC校验错误的报文 | 防御性编程 |
| **时间跳变** | 运行中修改系统时间 | 长时间运行稳定性 |
| **依赖缺失** | 删除某个DLL后启动程序 | 可靠性与鲁棒性 |

## 9.3 单元测试实战：xUnit与Moq

### 9.3.1 可测试性架构：依赖注入

为了隔离硬件依赖，必须遵循第4章提出的**依赖倒置原则**：

```csharp
// ❌ 不可测代码（硬编码依赖）
public class PlcWorker {
    private SerialPort _port = new SerialPort("COM1"); // 无法在测试中实例化
}

// ✅ 可测代码（依赖注入）
public interface IConnection { void Open(); byte[] Read(); }

public class PlcWorker {
    private readonly IConnection _connection;
    public PlcWorker(IConnection conn) { _connection = conn; } // 注入接口
}
```

### 9.3.2 模拟异常：测试重试逻辑

工业软件必须能处理通信超时。使用Moq模拟"前两次超时、第三次成功"的场景：

```csharp
[Fact]
public void ReadData_ShouldRetry_WhenTimeoutOccurs() {
    // Arrange
    var mock = new Mock<IConnection>();
    mock.SetupSequence(x => x.Read())
        .Throws(new TimeoutException())
        .Throws(new TimeoutException())
        .Returns(new byte[] { 0x01 });

    var worker = new PlcWorker(mock.Object);

    // Act
    var result = worker.ReadWithRetry(); 

    // Assert
    Assert.NotNull(result);
    mock.Verify(x => x.Read(), Times.Exactly(3)); // 验证确实重试了3次
}
```

### 9.3.3 项目实战：测试核心判定算法

第5章设计的`TestManager`中，`CheckStartCriteria()`方法包含复杂的判定逻辑（温度稳定、漂移达标）。每次修改都可能引入逻辑错误——单元测试是唯一的安全网。

```csharp
public class TestMasterLogicTests
{
    [Fact]
    public void CheckStartCriteria_ShouldReturnTrue_WhenTempIsStable750()
    {
        // Arrange：模拟10分钟恒定750℃数据
        var master = new TestableTestMaster();
        for(int i = 0; i < 600; i++) {
            master.Y1Data.Enqueue(750.0);
            master.Y2Data.Enqueue(750.0);
        }

        // Act
        bool result = master.CheckStartCriteria();

        // Assert
        Assert.True(result, "温度恒定750℃时应满足开始条件");
    }

    [Fact]
    public void CheckStartCriteria_ShouldReturnFalse_WhenDriftTooHigh()
    {
        // Arrange：模拟温度从750线性上升到755（漂移5℃ > 标准允许的2℃）
        var master = new TestableTestMaster();
        for(int i = 0; i < 600; i++) {
            master.Y1Data.Enqueue(750.0 + 5.0 * i / 600.0);
        }

        // Act & Assert
        Assert.False(master.CheckStartCriteria(), "漂移超过2℃时不应满足条件");
    }
}
```

> ⚠️ **注意：测试是第6章CI/CD的基础**
>
> 第6章配置的GitHub Actions流水线中，`dotnet test`这一步运行的就是本节编写的单元测试。每次代码提交都会自动执行所有测试——如果某次修改破坏了判定逻辑，CI会立即报红。

## 9.4 仿真测试：SIL与HIL

### 9.4.1 软件在环（SIL）

在没有物理硬件的情况下，通过第5章设计的`MockSensor`模拟硬件行为，在开发者笔记本上跑通90%的业务逻辑。

本项目已内置仿真器`SensorSimulator`，可以编写集成测试模拟完整的试验流程：

```csharp
[Fact]
public void Simulation_FullCycle_ShouldReach750()
{
    var simulator = new SensorSimulator(new SimulationConfiguration { 
        InitialFurnaceTemp = 25.0, TargetFurnaceTemp = 750.0 
    });
    simulator.StartHeating();

    // 模拟30分钟（加速模式）
    for(int sec = 0; sec < 1800; sec++) {
        simulator.Update(sec);
    }

    // 验证是否达到目标温度
    Assert.InRange(simulator.FurnaceTemp1, 740, 760);
}
```

> 🔍 **案例实战：SIL的工业价值**
>
> 修改了第5章的PID算法后，不需要去车间烧炉子，直接跑一遍SIL测试就能知道新算法是"超调"了还是"收敛"了。这也是第7章Mock First策略的直接体现。

### 9.4.2 硬件在环（HIL）

控制器是真实的，但受控对象（电炉）是仿真的。用另一台PC运行仿真模型，通过串口对接上位机，测试PID控制算法在真实通信链路下的表现。

## 9.5 测试文档编写规范

根据IEEE 829标准，一份专业的测试文档是项目交付的关键。

### 9.5.1 测试计划

| 要素 | 内容 |
|------|------|
| **测试范围** | 串口通讯模块、温度曲线模块、报警模块、报告生成模块 |
| **环境配置** | Windows 10, .NET 6.0, SQL Server Express, 虚拟串口对(VSPD) |
| **测试工具** | xUnit(单元测试), SensorSimulator(SIL仿真) |
| **验收标准** | 引用第3章SRS中的验收标准 |

### 9.5.2 测试用例模板

| 用例ID | 模块 | 优先级 | 前置条件 | 操作步骤 | 预期结果 | 实际结果 | 判定 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| TC-001 | 通讯 | High | 串口关闭 | 选COM1→点击"打开" | 按钮变灰，状态栏显示"已连接" | 同预期 | Pass |
| TC-002 | 报警 | High | 串口已连 | 发送超限温度值 | 红色闪烁报警 | 界面无反应 | **Fail** |
| TC-003 | 鲁棒 | Medium | 串口已连 | 物理拔掉串口线 | 提示"连接中断"，不崩溃 | 程序退出 | **Fail** |

### 9.5.3 缺陷报告

> 🔍 **案例实战：一份工业级缺陷报告**
>
> **标题**：[P0-致命] 接收超高温数据时未触发声光报警
> **重现步骤**：连接串口 → 设置报警阈值200 → 模拟发送温度201
> **实际结果**：温度数值更新但背景未变红，蜂鸣器未响
> **风险评估**：可能性=高（传感器故障时常见），影响=极高（安全事故）
> **结论**：**Must Fix**——否则严禁产品出厂（对应第7章P0级Bug处理流程）

## 本章小结

本章构建了工业软件的质量保证体系，从测试设计到测试执行，从单元测试到系统级仿真，确保软件经得起工业现场的考验。

**关键知识点**：

*   V模型将开发阶段与验证阶段一一对应——第3章的需求对应PQ，第5章的设计对应IQ
*   边界值分析、决策表、故障注入是工业测试的三大设计方法
*   xUnit + Moq实现硬件隔离测试，第4章的依赖倒置原则是可测试性的基础
*   SIL仿真让你不用烧炉子就能验证PID算法
*   测试文档是交付的关键组成部分，缺陷报告必须包含风险评估

**与前后章节的关系**：
*   第3章定义了验收标准 → 本章的测试用例逐项验证这些标准
*   第5章设计了核心类 → 本章的单元测试覆盖这些类的关键逻辑
*   第6章搭建了CI/CD → 本章的测试自动集成到每次构建中
*   本章验证了代码质量 → 第10章将进行项目总结和技术报告编写
