## 6.1 软件配置管理基础

在工业软件开发中，配置管理不仅是代码管理，更是**质量保证**和**可追溯性**的基石。回顾第5章的审计追踪需求——"谁在什么时候修改了什么"——版本控制正是在代码层面实现这一需求的工具。

### 6.1.1 核心概念

**配置项（Configuration Item）**

SCM管理的对象不仅仅是代码：

| 类别 | 示例 | 说明 |
|------|------|------|
| 代码 | `.cs`源文件、`.csproj`工程文件 | 核心管理对象 |
| 文档 | 需求规格说明书、设计文档、验收报告 | 第2-5章的产出物都应纳入版本控制 |
| 环境 | 编译器版本、第三方库、数据库脚本 | 确保构建环境可复现 |
| 工业特有 | PLC固件版本、PID参数默认值、电气原理图 | 区别于通用软件的关键 |

**基线（Baseline）**

基线是经过正式评审和批准的配置项集合，未经变更控制流程不得修改：

*   **功能基线**：第3章需求分析结束时建立
*   **设计基线**：第5章详细设计评审通过后建立
*   **产品基线**：出厂验收（FAT）通过后建立

**语义化版本号（Semantic Versioning）**

工业软件版本号 `X.Y.Z` 必须有严格定义：

| 位 | 含义 | 工业场景示例 |
|----|------|-------------|
| **X (Major)** | 架构重大变更，不兼容旧硬件 | 需停产升级 |
| **Y (Minor)** | 新增功能，兼容现有硬件 | 可在线升级 |
| **Z (Patch)** | Bug修复，不影响功能逻辑 | 紧急热修复 |

> 📘 **知识拓展：版本号与第3章"需求冻结"的关系**
>
> 回顾第3章提到的"需求冻结"里程碑——冻结后的任何变更都需要走CR流程。在版本控制中，这对应的就是建立"功能基线"并打上Tag（如`v1.0.0-requirements-approved`）。此后的任何修改都体现为新的提交记录，便于追溯。

## 6.2 Git版本控制实践

Git是目前全球最流行的分布式版本控制系统。与集中式的SVN不同，Git的每个开发者本地都有完整的仓库——这也是工业现场首选Git的原因：**可以在没有外网的车间内进行完整的版本控制**。

### 6.2.1 项目初始化

**最重要的文件：.gitignore**

切勿将编译产物或用户配置提交到仓库：

```gitignore
# 编译输出
[Bb]in/
[Oo]bj/

# 用户级配置 (不要提交!)
*.suo
*.user

# 临时文件
*.log
*.tmp
```

> ⚠️ **注意：工业项目的.gitignore特殊性**
>
> 工业项目中，现场配置文件（如串口号、PID参数）通常**不应提交**到仓库——不同现场的配置不同。应提交一个 `config.example.json` 作为模板，现场工程师据此创建实际配置文件。

### 6.2.2 日常操作与"救命"指令

| 场景 | 命令 | 说明 |
|------|------|------|
| **冲突解决** | `git pull` → 手动编辑冲突 → `git add` → `git commit` | 两人同时改了同一文件 |
| **撤销未提交的修改** | `git checkout .` | ⚠️ 危险：所有修改丢失 |
| **撤销已提交但未推送** | `git reset --soft HEAD^` | 保留代码，只撤销提交 |
| **撤销已推送的错误** | `git revert <commit_id>` | 生成反向提交，**严禁**用`reset --hard` |
| **精准搬运某个修复** | `git cherry-pick <commit_id>` | 只把Bug修复搬到release分支 |

> 🔍 **案例实战：一次真实的冲突解决**
>
> 小张和小李同时修改了第5章设计的 `PIDController.cs` 中的 `Compute` 方法——小张优化了抗积分饱和逻辑，小李修改了输出范围。`git pull` 后出现冲突标记 `<<<< HEAD ... >>>> branch`。正确做法是：打开文件，理解双方的修改意图，**合并两个人的改动**（而不是简单选一个），然后标记解决。

### 6.2.3 大文件管理

工业项目常有 `.dwg`（CAD图纸）或 `.pdf`（说明书）等大文件，应启用 **Git LFS（Large File Storage）**，防止仓库体积膨胀。

## 6.3 工业级分支管理策略

工业项目的交付流程包含严格的**FAT（出厂验收）**和**SAT（现场验收）**环节，分支策略需要与之对应。

### 6.3.1 分支定义

| 分支 | 用途 | 规则 |
|------|------|------|
| **master** | 现场稳定版本 | 仅允许从release分支合并，Tag示例：`v1.0.0-SAT` |
| **develop** | 日常开发 | 所有feature分支汇入此处 |
| **release/vX.Y** | FAT验收分支 | 从develop切出，**只允许修Bug**，不加新功能 |
| **feature/xxx** | 功能开发 | 从develop切出，完成后合并回develop |
| **hotfix/xxx** | 紧急修复 | 从master切出，修复后同时合并回master和develop |

> 💡 **想一想**
>
> 回顾第4章的技术选型——我们选择了C#和Modbus RTU。如果未来某个客户要求支持Modbus TCP（第4章排除的方案），应该在哪个分支上开发？是feature分支还是site分支？

### 6.3.2 离线协同（Air-Gapped Workflow）

许多工厂车间物理隔离，没有网络。Git的 `bundle` 命令可以解决这个问题：

```bash
# 在有网的办公室：打包分支更新
git bundle create update_v1.bundle HEAD master

# 在车间现场：从U盘拉取更新
git pull /e/update_v1.bundle master
```

> 📘 **知识拓展：为什么工业现场常常没有网络？**
>
> 在军工、化工、核电等行业，生产网络与办公网络物理隔离是安全合规的强制要求。这正是第1章提到的工业软件"高可靠性与安全性"特征在工程实践中的体现。

## 6.4 持续集成与持续部署（CI/CD）

哪怕是桌面软件，引入CI/CD也能避免"在我电脑上能跑，在工控机上跑不起来"的尴尬。

### 6.4.1 自动构建流程

| 步骤 | 命令 | 说明 |
|------|------|------|
| **Restore** | `dotnet restore` | 还原NuGet包 |
| **Build** | `dotnet build` | 编译解决方案 |
| **Test** | `dotnet test` | 运行单元测试 |
| **Publish** | `dotnet publish -r win-x64 --self-contained` | 生成独立部署版本 |

### 6.4.2 GitHub Actions实战

在项目根目录创建 `.github/workflows/dotnet-desktop.yml`：

```yaml
name: Industrial WinForms Build

on:
  push:
    branches: [ "master", "develop" ]
    tags: [ "v*" ]

jobs:
  build:
    runs-on: windows-latest

    steps:
    - uses: actions/checkout@v3
    - uses: actions/setup-dotnet@v3
      with:
        dotnet-version: 6.0.x

    - name: Restore
      run: dotnet restore
    - name: Test
      run: dotnet test --no-restore
    - name: Publish
      run: dotnet publish -c Release -r win-x64 --self-contained true -o ./publish
    - name: Upload Artifact
      uses: actions/upload-artifact@v3
      with:
        name: ISO11820-System-v${{ github.run_number }}
        path: ./publish
```

## 6.5 工业软件发布策略

工业软件的升级比互联网软件更谨慎——错误的升级可能导致停产。

> ⚠️ **注意：切忌全厂一键升级！**
>
> 工业软件发布应遵循**灰度发布**策略：
> 1. **Alpha阶段**：仅升级实验室的一台机器，验证基本功能
> 2. **Beta阶段**：升级现场一条非关键产线，运行24小时
> 3. **GA阶段**：确认无问题后，全厂推广
>
> 这与第2章风险评估中提到的"减轻策略"一脉相承——通过小范围试点降低风险影响。
